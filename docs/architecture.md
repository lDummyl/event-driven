# Архитектура

Event-sourcing демо: вечный append-only лог фактов + пересобираемая проекция в in-memory H2.
Цель документа — зафиксировать модель, инварианты и «швы роста», чтобы позже не переписывать ядро.

## 1. Модель

```
   команда ──► [решить] ──► факт(ы) ──► (сохранить) ──► проекция(и)
   intent      логика       event/       EventStore      UserState (H2)
   транзиент                факт         (файл)          производное
```

- **Факт (event)** — то, что случилось. Единственный источник правды. Иммутабелен, append-only.
- **Команда** — намерение. Транзиент; не является источником правды и **никогда не реплеится как команда**.
- **Проекция** — производное представление (`UserState` в H2). Disposable: пересобирается из лога.

## 2. Инварианты

1. Лог — единственная правда. Всё остальное — производное.
2. Реплей **применяет**, а не **решает**. Если на реплее нужно «решать» — это command sourcing (запрещено).
3. Команды не хранятся как правда и не выполняются повторно.
4. Сайд-эффекты не выполняются на rebuild (см. `Mode`).
5. Схема события эволюционирует **upcaster'ами** (в одну сторону), а не переписыванием лога.

## 3. Виды событий и дерево решений

`EventKind`:

- `RECALCULABLE` — эффект не доверяем, на rebuild пересчитываем **текущей** логикой (пример: очки за донат).
- `FROZEN` — исторический факт, применяем **как записан**, без повторной валидации (пример: старый username).

```
Эффект = чистая функция от (raw input + данные-правила)?
   да  → RECALCULABLE (обратная сила возможна, правило — данные)
   нет → FROZEN (полный эффект пишется фактом)
Исключения («аксакалы») → отдельный факт-исключение, читается текущей политикой
```

## 4. Конверт события и версионирование

Каждый факт несёт `EventMetadata`:

| Поле | Назначение |
|---|---|
| `id` | идентификатор факта (идемпотентность/dedup) |
| `correlationId` | связь «запрос ↔ ответ» |
| `causationId` | чем факт порождён (трассировка причин) |
| `aggregateId` | к какому агрегату относится |
| `occurredAt` | время |
| `schemaVersion` | версия схемы payload (стартует с 1) |

В NDJSON-логе конверт хранится отдельно от payload (`EventLogEntry`); payload содержит только
поля события. Будущие поля конверта не потребуют правок в каждом событии.

## 5. Режимы и сайд-эффекты

`Mode`:

- `ONLINE` — живая обработка; эффекты могут выполняться.
- `REBUILD` — пересборка; эффекты **обязаны молчать**.

`EffectPort` — пустой интерфейс-маркер под будущие адаптеры (email, платежи, webhooks). Каждая
реализация обязана смотреть на `EventRouter.currentMode()`. Outbox намеренно не реализован.

## 6. Швы роста (заложены, но не построены)

| Будущая деталь | Шов |
|---|---|
| Смена схемы события | `schemaVersion` + upcasters |
| Переезд хранилища (БД/брокер) | порт `EventStore` |
| Дубли при доставке | `eventId` + `UserStateService.applyIfNew` |
| Сайд-эффекты / outbox | `Mode` + `EffectPort` |
| Мультиюзер/мультиэнтити | `aggregateId` + `EventStore.byAggregate` |
| Трассировка причин | `correlationId` / `causationId` |
| Версии правил (обратная сила) | `RatingProperties` как будущий `Policy`-порт |
| Сплит на сервисы | событийная коммуникация + описанные границы |

## 7. Границы контекстов (описаны, код не разбит)

- **donation** — владеет `DonationReceived`, `DonationService`, правилом начисления.
- **user-profile** — владеет `UsernameChanged`, `UsernameChangeRejected`, `EmailChange*`,
  `UserPrimalDataService`, политиками username/email.

Правила: контекст владеет своими событиями; чужие проекции напрямую не читать; общение — событиями.
Физическое разделение на пакеты/сервисы отложено до появления реальной боли.

## 8. Явные non-goals

command bus, command sourcing, версии политик, upcasters, outbox, saga, микросервисы, Kafka, snapshots.

## 9. Сценарии

- **Обратная сила (#2):** поменять `app.rating.points-per-100`, перезапустить/`rebuild` → очки
  пересчитываются по новому правилу (`RECALCULABLE`).
- **Аксакалы:** `seedLegacyUsername("12345")` → онлайн-смена отклоняется новым правилом, после
  `rebuild` исторический факт применяется (`FROZEN`).
- **Email-корреляция:** онлайн-смена пишет `Requested` + `Result` с общим `correlationId`; на
  rebuild берётся записанный исход, без повторной валидации.
